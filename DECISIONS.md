- D-02 Mac target: M1, 8 GB, macOS 13.6.9; Apple Silicon only, deployment target 13.0.
- D-03 Licence: GPL-3.0-or-later.

## Environment and toolchain

- D-10 Rust uses the `x86_64-pc-windows-gnu` host with WinLibs GCC (MSVCRT), not MSVC: installing Visual Studio Build Tools needs an administrator (UAC) prompt nobody is here to approve, and the WO allows only per-user toolchain installs. Side benefit: with static libgcc/libstdc++ the exe needs no Visual C++ runtime on a clean Windows 11 PC.
- D-11 Toolchains are installed per user (rustup with `--no-modify-path`, winget portable packages for uv and WinLibs). Nothing changes the system PATH; `scripts/devenv.sh` sets PATH per shell.
- D-12 PyTorch 2.14.1+cu130 on Python 3.12: verified with a real matmul and STFT on the RTX 5070 Ti (compute capability 12.0, sm_120 in the wheel's arch list). Python 3.12 rather than the system 3.14 for the widest wheel coverage of audio/ML packages.
- D-13 Heavy local state (Python runtimes, venv, model cache, datasets) lives in `../jukeoke-build/`, outside the repository.

## Architecture (see docs/ARCHITECTURE.md)

- D-20 App shell: Tauri 2 + Rust core + Preact/TypeScript UI, as the WO suggests. Small, one codebase, no framework symlinks in the Mac bundle (exFAT-safe).
- D-21 Song file: a small custom chunked container rather than ZIP, because it has two fixed-size settings slots that are updated in place with an A/B sequence number and checksum. Changing the key or the mix then writes a few KB instead of rewriting a 100 MB file, and a stick pulled mid-write can only damage the slot being written. A ZIP cannot do that without breaking its own CRCs.
- D-22 Stems are stored as 24-bit FLAC with a per-stem gain chosen so the peak sits below full scale (headroom kept, gain stored), as WO section 5 asks. 24-bit quantisation noise is about -144 dBFS.
- D-23 The pitch shifter runs on one stereo mix bus (lead x guide + backing + other) instead of per stem: same result for a linear mix, a quarter of the CPU on the M1. Drums bypass it through a latency-matched delay.
- D-24 At 0 semitones the pitch bus bypasses Rubber Band (bit-transparent mix), with an equal-power crossfade to the shifted path when the key changes. Fidelity first.
- D-25 Heavy DSP runs in a render-ahead worker about 150 ms ahead of the device; the device callback only copies and applies master volume. Generous headroom for a fanless, throttling M1.
- D-26 The Studio writes `.jksong` with its own small Python writer; Rust has a reader and writer. Two independent implementations of the spec, cross-checked by tests.

## Stage 0 results (2026-11-17)

- D-30 Rubber Band 4.0.0 vendored unmodified; built-in FFT and resampler forced on every platform (#error guards against vDSP/IPP/FFTW/fast-math), so the Mac runs the same code as Windows. Pitch option HighQuality, formants shift with pitch.
- D-31 DEVIATION from ARCHITECTURE 4 (now updated): every key change crossfades (40 ms, equal-power) between two fixed-pitch R3 instances; no running setPitchScale. Measured: R3's start delay depends on the pitch scale, so a running change would slide the band against the unshifted drums. Rubber Band is idle at 0 semitones; a new instance is primed with 4096 frames of real audio (Rubber Band 4.0.0's reset() is incomplete, measured diff up to 0.25).
- D-32 One graph latency L = longest R3 FFT x 9/8 (4608 frames at 44.1/48 kHz, 9216 at 88.2/96 kHz). Drum and bypass delays equal L exactly; per-key transient-bias tables correct R3's systematic transient placement. Result: drum path offset 0; band-vs-drum mean offset at most 13.6 samples (0.31 ms); single impulses jitter up to +-2 ms at -12. Exactly 0 is not possible through a phase vocoder; drums vs band at +-5/+-12 goes on the listening checklist.
- D-33 Rubber Band is always fed 256-frame chunks (its real-time output depends on chunking); output is bit-identical for any block size. Pitch scales come from a correctly rounded table, transcendental maths in jk-dsp from the pure-Rust libm crate. Cross-platform tolerance: max |diff| 1e-5, RMS -110 dB.
- D-34 A key change is heard about 280 ms after the click (150 ms render-ahead + L 104.5 ms + device buffer). No click; acceptable for a key control. Recorded for the owner.
- D-35 Output resampler: rubato 5.1 sinc (256 taps, Blackman-Harris^2, 256x oversampling, cubic), only when device rate != song rate. Measured THD+N -133.8 dB. Note: R3 itself resamples internally with its "FastestTolerable" BQResampler (about 90 dB SNR) during pitch shifting; that is inside Rubber Band's best engine and not configurable without patching it.
- D-36 WASAPI shared mode at the device mix format (no Windows resampling); exclusive mode tries the song rate first (f32, i32, i24, i16). MMCSS "Pro Audio" on device and render threads. Render worker 150 ms ahead, stem rings 4 s, 10 ms fade-in.
- D-37 macOS audio output via cpal pinned to 0.16: cpal 0.17+ links the macOS 14.2 process-tap API (found by the verifier; a Windows type-check cannot see it). The final Mac binary's imported symbols still need checking in CI.
- D-38 Own minimal FLAC encoder in jk-engine for fixtures (flacenc's Rice parameter cap produced a 24 GB file). The Studio writes FLAC via libsndfile.
- D-39 Tauri 2.12 on x86_64-pc-windows-gnu needed two fixes: an in-house WebView2 loader in C (app/src-tauri/native/webview2_loader.c, GPL) instead of Microsoft's WebView2Loader.dll, and our own application manifest (MinGW's default manifest shadowed). Exe 6.0 MB stripped, imports only Windows system DLLs. Workspace rust-version raised to 1.90 (Tauri needs it).
- D-40 Portable root: the parent of a folder named `Windows` (or `Mac` holding the .app) that contains `Library/` or `portable.txt`. Names compared case-insensitively. No unbounded upward walk (it would find ~/Library on macOS). WebView2 profile in `<root>/Settings/webview-windows`; macOS web view is non-persistent (incognito).
- D-41 WO 4.8 "write nothing to the registry" cannot hold literally: the WebView2 runtime updates its shared HKCU EdgeUpdate `lastrun` value on every launch, and Explorer records MuiCache entries for any windowed exe path. Neither names our app's data; the app itself writes nothing. Reported to the owner.
- D-42 macOS type-checking from Windows uses Zig (PyPI `ziglang`, MIT) as the C compiler only for objc2-exception-helper; no Apple SDK involved.
- D-43 CI targets macos-15 (arm64): GitHub retired macos-14 on 2026-11-02, so it is the oldest Apple Silicon image. Neither macOS 13 nor 14 can be tested in CI; the self-check on the owner's Mac is the real test.
- D-44 Web-view baseline stays Safari 16.4. The true floor on 13.6.9 is WebKit 16.6 (13.6 did not update Safari); separately installed Safari updates can reach 18.6. The self-check records the real version. Build check: every emitted JS file must parse as ES2022.
- D-45 ScreenCaptureKit: capture at the device's nominal rate if SCK supports it (8, 16, 24 or 48 kHz), else 48 kHz with a plain note; the file format comes from the first real buffer. 2x2 px video at 1 fps, discarded. Recordings are float WAV (RF64 above 4 GiB) written progressively to the final path (header patched every 1 s) so a pulled stick loses at most ~1 s.
- D-46 Song file library: serde_json `float_roundtrip` enabled (gains must survive a rewrite bit-exactly). Settings that do not fit the slot trigger a full rewrite with a larger slot. Unknown keys preserved at every level.

## Lyrics, alignment and analysis (2026-11-17)

- D-50 Alignment model: facebook/wav2vec2-large-960h-lv60-self (Apache-2.0, 1.26 GB). HuBERT-xlarge (Apache-2.0, 3.85 GB) measured the same, so the smaller one is default (WO: prefer the more permissive/smaller when close). MMS aligners excluded (CC-BY-NC-4.0).
- D-51 Own CTC forced alignment (numpy Viterbi), no torchaudio (its forced-align API is deprecated). Aligned against the isolated lead vocal: on the full mix the mean error is 3.5 s instead of 0.21 s.
- D-52 LRC/online line times become windows (start - 1 s, next + 1 s); a constant LRC offset (another edit of the song) is detected and corrected (0.5-15 s tested: 94.7 % within 0.3 s instead of 15 %). An offset affecting only part of a song is not solved (warning only).
- D-53 Held notes: the last letter of a word extends through the hold while the lead stem stays within 15 dB of its loud level. Halves the median word-end error (0.101 -> 0.050 s).
- D-54 Transcription: faster-whisper 1.2.1 / CTranslate2 4.9 with large-v3-turbo (MIT), fp16, VAD off (it dropped sung passages). WER 26.6 % on 20 songs: transcribed lyrics are always labelled unchecked. CTranslate2 needs CUDA 12 cuBLAS beside torch cu130 (nvidia-cublas-cu12, 737 MB, NVIDIA EULA, redistributable).
- D-55 Key: librosa CQT chroma vs Albrecht-Shanahan profiles; 100 % on clear cadences, 66.7 % on synthetic pop progressions, 59-80 % on real guitar. Shown as a suggestion; the saved value is the shift in semitones, which works whatever the detected name. Tempo is informational.
- D-56 Analysis/alignment use their own mono 16/22.05 kHz copies (soxr VHQ); these never touch a stem, so they are not listed as stem resampling.

## Stage 1 (player side), 2026-11-17

Engine (jk-engine, jk-dsp). Evidence: docs/benchmarks/playback.md. Windows only; the macOS path is type-checked only.

- D-57 The output stream stays open from `Engine::new` until a device switch or drop and plays silence when idle; pause, seek and song change never stop it. Reopening a device takes 73-640 ms here and would cut the clock; with a running stream a seek or pause is only a fade.
- D-58 Seek is in place, by generation: control fills a new stem ring from a sample-accurate decoder seek starting `prime_len` frames before the target (real audio primes Rubber Band), the worker writes `Start`/`End` markers into a second SPSC ring, and the callback fades the old audio out (10 ms), drops the rest of that generation, waits for 50 ms of the new one and fades in (10 ms, integer frame counter so a fade ends exactly at 0 or 1). Measured: about 40-49 ms seek latency at the DAC; bit-exact at key 0 and on the drum path at +3, not on the shifted band (phase-vocoder state differs), which is acceptable after a seek.
- D-59 Playback clock = a span log of what the callback wrote (song audio from p, or silence at p), walked back by the device-reported latency (frames queued + stream latency). Replaces Stage 0's frames-delivered formula because it stays right across pause, seek, underrun and song end. `Snapshot.position_ns` carries the callback time for extrapolation. 20-min soak: clock -20.92 ppm against the device's own -20.82 ppm.
- D-60 DEVIATION from ARCHITECTURE 4 (now updated): Rubber Band instances are built on a low-priority house-keeping thread and offered to the graph through an SPSC ring (2 spares); replaced instances, old rings, songs and resamplers return through a garbage ring and are freed there. The render worker never allocates or frees (measured: 0 instances built on it); a key change with no spare waits (`deferred_blocks`). A never-fed instance is reused, not replaced (construction leaves R3 in JustCreated mode). The offline renderer still builds inline; output is identical.
- D-61 symphonia-bundle-flac 0.6.1 keeps stale packet-parser state when a seek lands exactly on a frame start and silently decodes wrong samples, so `FlacStem` rebuilds its demuxer and decoder on every seek. jk-format's `StemDecoder::seek` has the same bug and `verify` compares only 64 frames after a seek (open). UPDATE 2026-11-17: jk-format's StemDecoder::seek now rebuilds its demuxer on every seek too (fixed; 1336 seeks bit-exact on a 4-minute song).
- D-62 Unknown stem roles (SONG_FORMAT forward compatibility): pitched in-mix stems are summed at unity into an extra pitch-bus input, unpitched ones into an extra drum-bus input, stems not in the mix are not decoded. With no extras the bits equal the v1.0 routing, so an older player plays a newer file the same way.
- D-63 `set_params` while paused re-renders the buffered audio (an in-place seek to the current position), so play starts with the new key and mix instead of ~150 ms of the old. Pending params are cleared on song load and unload (verifier fix: params sent with no song loaded leaked into the next song, 3.35 M wrong samples).
- D-64 Devices: `Engine::new` never fails for a missing device (`play()` returns `no_device`); a saved device that is gone falls back to the default; device loss pauses, keeps the position, emits `DeviceLost`, and `play()` reopens. Opening tries the chosen device as asked, the same device in shared mode, the default in exclusive mode, then the default in shared mode, and returns `exclusive_unavailable` when it fell back (verifier fix: a refused exclusive mode used to leave no output; the refusal branch has not run on hardware). A failed `set_device` reopens the previous device. Ids `null` / `null:<rate>` are a silent real-time device for tests and the headless self-check.
- D-65 Engine errors carry stable codes (`no_device`, `device_not_found`, `device_failed`, `device_lost`, `exclusive_unavailable`, `song_not_found`, `song_unreadable`, `song_newer_version`, `song_damaged`, `song_truncated`, `not_loaded`, `write_failed`, `cancelled`, `invalid_argument`, `internal`) plus a plain message, so the app can show them as they are.
- D-66 Output peak and clipping are measured in the render worker (max of 6 x 50 ms windows, times master volume), not in the callback, and nothing limits (WO 5). A clip epoch bumped by load, `set_params` and `set_master` clears the latch and holds it off for graph latency + crossfade + 20 ms + one block, so old-mix audio cannot re-light the lamp after the singer lowers a level (verifier fix).
- D-67 Export scaling rule: Wav32f is the render bit for bit, never scaled (JUNK chunk becomes ds64 for RF64 above 4 GiB). Flac24 renders once into a temporary float file, measures the peak and scales down only when it exceeds 8388607/8388608, rounding without dither; the gain is reported (`applied_gain_db`) so the UI can say so, and the FLAC is decoded back and MD5-checked. One render instead of two halves export time at a non-zero key (58 -> 28.8 s for 4 min). Measured: Flac24 within half a 24-bit LSB of the render; 111x real time at key 0, 7.5x at +3.
- D-68 The in-house FLAC writer (D-38) now streams and writes the STREAMINFO MD5 (jk-format `verify` requires it), one seek point per second, wasted bits and RICE/RICE2 as needed.
- D-69 Demo song: generated "Twinkle, Twinkle, Little Star" (public domain), 40 s with an 8 s instrumental break, 44.1 kHz mono stems as 24-bit FLAC carrying 16 significant bits (2.4 MB, deterministic, `jukeoke-cli make-demo-song`), C major, 120 BPM. Letter times exact by construction (onset/coda consonants 60 ms, extra nucleus vowels 80 ms, the first vowel holds, punctuation zero length, each syllable sung over 90 % of its note), so it is the ticker's ground truth and the self-check's test song. Over the fixtures' 600 KB guideline; exception documented in tests/fixtures/generated/README.md.

Recorder (jk-recorder, Windows WASAPI loopback). Evidence: docs/benchmarks/recorder.md.

- D-70 The recording spans the instants `Recorder::start()` and `stop()` are called, on both platforms. Set-up time before the OS stream runs (9-454 ms measured) and any time without packets are filled with digital silence, so the length equals the caller's wall clock (measured equal within 1 ms). WO trap 5.
- D-71 Gap fill from QPC timestamps: loopback packets are stamped 9.8-10.6 ms ahead of read time, so Start and Stop are shifted onto the packet timeline by the first packet's lead and the packet straddling Stop is held back and cut there. Measured length vs Start..Stop, all within one 10 ms packet: 20 s with 8 s of total silence -18.8 frames (keep-alive on) / -74.8 (off, a 7.73 s hole filled); 10 s started and stopped in silence -10.9 / -0.1 (Windows sent 0 packets in 10.1 s). Verifier re-run: -18.3 / -64.0 / -10.5 / -54.0. Open: a late first packet moves that lead's worth of audio at the edges.
- D-72 A silent keep-alive render stream is on by default (shared mode, 100 ms buffer, every buffer flagged AUDCLNT_BUFFERFLAGS_SILENT, topped up every 25 ms on its own thread). It keeps the endpoint running, so Windows keeps sending packets and does not fade out the last 15-25 ms of a sound before silence (verifier finding). Side effect: with Windows effects active, silent stretches hold their noise floor (-120 to -180 dBFS peak) instead of exact zeros.
- D-73 Capture is a bit copy of the shared mix format (48 kHz, 2 ch, f32 here); the RAW stream option is not used (measured: no effect). Loopback taps after Windows "Audio enhancements" (on this PC EQ, bass boost and speaker compensation: about +2.9 dB below 125 Hz, -3.0 dB above 8 kHz), so the capture is NOT bit-identical to what was played (max diff 7.98e-4 on a 9.77e-4 signal; residual after a linear fit about -125 dBFS RMS), while the recorder's own packet-to-file path is bit-exact. Reported, not forced; no Windows setting was changed. Owner advice: turn Audio enhancements off for the device (expected bit-identical, not verified).
- D-74 Windows declares the capture format at Start, so the file exists from Start and an all-silent recording is still full length; if the OS stream then fails, that empty file (only one this recorder created with create_new) is deleted. A mid-recording format change or a lost device sets state Failed with a plain message and closes the file at once (measured: a valid WAV on disk before `stop()`).
- D-75 Capture real-time path: buffer pool of 32 x 100 ms filled when the format is declared, stats from atomics, event-driven loopback with a 200 ms buffer and MMCSS "Pro Audio"; measured 0 heap allocations in 5 s of steady recording (5/5 runs). Device queries from other threads run on a short-lived COM helper thread so the caller's apartment is untouched. wasapi 0.27 / windows 0.62, the versions jk-engine already uses.
- D-76 The loopback probe's test signal is 2^-11 (-66.2 dBFS) with a guard that stops if the captured peak exceeds -60 dBFS: loopback measures after Windows' effects, which had raised the earlier -60.2 dBFS signal to -58.0 dBFS (verifier fix; hard rule).

App core (app/src-tauri). Layout in app/src-tauri/README.md.

- D-77 The app drives the engine through `AudioEngine` / `Renderer` traits with fakes, so command logic, the clock thread and slot saving are tested without an audio device; the real engine is tested on `null:48000`.
- D-78 Every Tauri command is async on the blocking pool and declared `rename_all = "snake_case"`: plain commands run on the main thread, where a slow stick or a Studio start would freeze the window, and Tauri would otherwise expect camelCase arguments.
- D-79 The `playback://clock` thread runs on absolute 33.3 ms deadlines and is woken by player commands, because Windows' 15.6 ms timer had cut the rate to 17/s (now 29-31/s); while not playing it checks 4 times a second. `position_s` is extrapolated to the emit time from `Snapshot.position_ns` (capped at 100 ms).
- D-80 Per-song settings go to the song's slot debounced 1 s and are flushed on song change and exit. App settings are deep-merged, clamped, debounced 300 ms and written atomically; a wrongly typed or unknown value (e.g. an enum from a newer app sharing the stick) falls back alone to its default with a warning (verifier fix: it used to reset every setting), unknown keys are kept, an unreadable file is kept as settings.json.bad.
- D-81 Durable writes use unique temp names `<name>.tmp-<pid>-<counter>-<random>`; Windows renames with MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH), its equivalent of a directory fsync, retried up to 0.5 s on access-denied or sharing violations (antivirus, indexer); Unix fsyncs the parent directory.
- D-82 Library: recursive scan with jk-format's helpers (skip dotfiles, `._*`, `*.tmp-*`); summaries cached by (size, mtime); song ids that could leave the Library (`..`, drive letters, backslashes, `:`, non-.jksong) are refused; unfinished `*.jksong.tmp-*` older than 1 h are deleted at start-up (younger ones may be a running Studio write). Watcher: notify, recursive (polling every 5 s if native watching fails), bursts coalesced over 400 ms into one `library://changed`; removed or renamed names count, so a folder moved to the Recycle Bin is seen (verifier fix).
- D-83 Studio supervisor: probed once in the background after start-up (`checking: true` until then; start timeout 60 s, requests 120 s); stopped after 10 min idle; after 3 crashes within 10 min the waiting jobs fail with a plain explanation instead of restarting in a loop; job ids are chosen by the app and jobs claimed under a lock so a cancel cannot race the send; queued jobs are re-sent after a crash; closing the app kills a Studio that is still starting. Production command `<root>/Windows/Studio/python/python.exe -I -X utf8 -m jukeoke_studio serve` (UTF-8 stdio whatever the code page) with `JUKEOKE_MODELS_DIR=<root>/Models` (verifier fix); dev uses the venv python without `-I` and `PYTHONPATH=<repo>/studio`; `JK_STUDIO_PYTHON` + `JK_STUDIO_SCRIPT` override it (fake Studio in tests). Open: per-user caches (HF_HOME, TORCH_HOME, CUDA_CACHE_PATH, TEMP) are not yet redirected to the stick.
- D-84 Self-check (WO 4.10), 8 items: System, Web engine, Memory, Output device, Test tone, Recorder, Demo song, Key change. Test tone: a generated 8 s 440 Hz song at 0.25 with master 0.004, exactly -60 dBFS peak; master is set 250 ms before loading so the engine's ramp ends on silence; `--silent` / `silent: true` uses master 0. Clock rate: wait up to 3 s for the clock to move, then time 1.2 s with the engine's callback timestamps (verifier fix: counting the start delay gave 0.891 and would fail on Bluetooth). Recorder: 3 s capture, length >= 2.9 s, <= call-to-stop + 0.05 s and within 0.98-1.02 of the OS start-to-stop (verifier fix). Key change: offline renders at +2 and -5, pitch within 5 cents and length unchanged. The user's song is unloaded and reloaded at the same position. Report `Settings/selfcheck-<local time>.txt`; `--selfcheck [--silent]` exits 0/1.
- D-85 Start-up failures never reach Tauri (it would turn them into a panic): `startup::report` writes Settings/logs/startup-error.txt, shows MessageBoxW (Windows) or an NSAlert via rfd (macOS) and exits 1. No dialog under `--smoke-test` / `--selfcheck`; a panic hook does the same during start-up and only logs afterwards.
- D-86 The WebView2 profile (`<root>/Settings/webview-windows`, 9.0 MB in 141 files measured) is kept between runs, because clearing it would rewrite it on every launch from a slow stick, but it is disposable: if window creation fails the folder is renamed aside, deleted and the window retried once (label `main-retry`). `WEBVIEW2_USER_DATA_FOLDER` is removed from the process environment before any thread starts, so nothing can move the profile off the stick.
- D-87 macOS translocation: with no remembered root the app runs in `DataMode::Translocated` (data in a temp folder) and the UI shows `translocation_help` and calls `root_choose`; the chosen folder (the stick root or its Library, never the home folder) is remembered in `~/Library/Application Support/org.jukeoke.app/root.txt`, the only write outside the stick, and the app restarts. Type-checked only.
- D-88 Extends D-41: Windows' audio service writes an entry under HKCU\Software\Microsoft\Internet Explorer\LowRegistry\Audio\PolicyConfig\PropertyStore for any exe that opens an audio stream; the portable audit lists it as OS-written, like MuiCache (control: the store already held entries for other exes).
- D-89 The demo song is bundled: build.rs copies it into app/src-tauri/resources/ (a Tauri resource; on Windows the dist needs `Windows/resources/`); a missing demo song is a build warning. A release build fails when app/ui/dist is missing or holds only the stub (`JK_ALLOW_UI_STUB=1` for unshipped builds).
- D-90 Naming: the key label is "A major → B major (+2)", with the arrow from WO 4.5 and the Studio's spelling (`+2 semitones` / `original key` when the key is unknown); the UI draws its own label with flat glyphs, so the two strings can differ (open, cosmetic). Exports are `<artist> - <title> (<key>[, <shift>]).flac|wav`, safe for Windows, macOS and exFAT, with ` (2)` suffixes. Recordings are `Recording <local time>.wav`; their clip flag lives in Settings/recordings-index.json because a WAV header cannot hold it. Recorder `elapsed_s` is wall time since Start (the media clock stands still while Windows sends no packets).
- D-91 Default settings, identical in core and UI: master 1.0 (unity, no hidden attenuation), lyrics text 56 px at 1440x900 scaled by min(w/1440, h/900) (at 64 px the 2 s lookahead rule shrinks fast songs more often), marker at 0.33, sung #ff3d8b, upcoming #f6efd9, marker mint #7dffd8 (it must stand out against the pink letters it has passed), skin and bubbles on, motion "system". The Bluetooth offset is per device id (`default` for the system default output).
- D-92 capabilities/default.json adds `core:window:allow-set-fullscreen` (stage full screen) and the `main-retry` window label; nothing else beyond `core:default`.

UI (app/ui)

- D-93 UI clock: every `playback://clock` event re-anchors a `performance.now()` model; errors under 250 ms are absorbed by changing speed by at most 5 % over about 0.5 s, larger ones snap; extrapolation stops 250 ms after the last event; a UI-requested pause freezes at once, an unrequested one glides back over 120 ms; after a UI seek while playing the display waits at the target until the engine is playing it (verifier fix: 23-39 ms ahead became 0.2-0.6 ms). Real app: mean 0.61 ms from the engine, never backwards.
- D-94 Ticker cells: each grapheme is measured and drawn at a fixed x (ligatures and `calt` off). A letter's cell is its glyph box plus at most half a neighbouring separator (space, line gap, zero-length letter), shared so average speeds are equal. Letter under the marker is tested on cells; the marker is on the glyph box itself 93.8 % of sung time (Twinkle).
- D-95 Ticker smoothing: Steffen's (1990) monotone cubic through every cell edge. Its speed is continuous and it never overshoots a knot, so the marker cannot leave the sung letter's cell (hard constraint by construction); peak speed / local average measured 1.99. Fixed letter widths still make the text surge on short consonants (about 24 letter-heights/s at peak in Twinkle): readability is for the owner's eye.
- D-96 Ticker breaks and lookahead: a line gap of dt seconds is v x dt wide with v = (width right of the marker) / 3 s, so the next line enters at the right edge 3 s before it is sung; long breaks exit, rest, then enter over the last 3 s; a countdown shows for rests of 4 s or more (intro included). If dense singing would leave less than 2 s of upcoming text on screen the font is scaled down for that song (floor 0.6x). Open: at extreme settings (marker 60 %, text 96-120 px) the floor is reached and lookahead falls to about 1 s. Lines with no words are dropped before layout (verifier fix: they crashed the ticker).
- D-97 Ticker renderer: 1024 CSS-px tiles per colour in device pixels, built lazily, LRU cache (about 2 screens + 4), next tile pre-rendered; each frame clears, blits both colours clipped at the marker, then draws the marker and countdown. 60 fps cap by advancing whole 16.67 ms periods (verifier fix: 75-165 Hz screens got 37-55 fps), stopped when idle or hidden. Font from CSS `--ticker-font` / `--ticker-weight` (skin: Atkinson Hyperlegible Next 700, awaited with `document.fonts.load` before measuring). Open: WebView2 reports a minimised window as visible, so the ticker still draws while minimised.
- D-98 Sync editor: tap-along stores lyric time = playback position at the tap minus song and device offsets, so a re-tapped line lands where it was heard; words keep their share of their slot and letters scale with their word. "Reset to original" reloads the song, because the API has no "original lyrics" query, and the editor rebuilds its draft from the reloaded lyrics (verifier fix).

## Studio pipeline and protocol server, 2026-11-17

Evidence: `studio/tests/test_server.py`, `test_media.py`, `test_pipeline_gpu.py`, `app/src-tauri/tests/studio_supervisor.rs`; protocol additions listed in docs/STUDIO_PROTOCOL.md section 11. Numbers D-140 onwards to stay clear of other streams' D-122+.

- D-140 Server threads: the main thread reads stdin and answers quick requests itself; `probe`, `inspect`, `lyrics.lookup`, `models.download`, `realign` each run on their own thread; one worker runs jobs in order. One GPU lock serialises separation, transcription, alignment and `realign`, so a sync-editor realign waits for the running stage instead of competing for VRAM (a 6 GB card would not hold both).
- D-141 Windows pipe trap: a thread blocked in a synchronous read of the stdin pipe blocks every other use of that pipe, including CreateProcess's handling of inherited standard handles. Measured: a stub job sat in the analyse stage for ~55 s until the test closed stdin (something in that stage starts a helper process; which library was not identified). Fix: the Studio duplicates the request pipe privately (non-inheritable) and points fd 0 / STD_INPUT_HANDLE at NUL; the same job then took 4.0 s. Stdout is likewise duplicated for the protocol and fd 1 / STD_OUTPUT_HANDLE point at stderr, so C-level prints never reach the protocol.
- D-142 Probe: standard-library fast path first (GlobalMemoryStatusEx, nvcuda.dll through ctypes: name, VRAM, compute capability), answered in milliseconds without importing PyTorch on a weak PC; only when the hardware passes, PyTorch is imported on a thread and a real GPU matmul checked against the CPU, waited for at most `timeout_s` (45 s default; "pending" after that instead of hanging). Thresholds 5632 MiB VRAM / 11264 MiB RAM so that cards and PCs sold as 6 GB / 12 GB pass (the default preset peaks at 4.1 GB). PyTorch is warmed up after `hello` when the hardware passes. Measured through the app's supervisor: start + probe 10.7 s on this PC.
- D-143 Decoding: PyAV, first audio stream (video files too), float32 by explicit scaling of the decoder's integer output (no FFmpeg resampler, so no conversion of any kind; 16/24-bit sources map exactly, tested for wav16/wav24/flac24/aiff/mkv-flac/avi-pcm). More than 2 channels are folded to stereo with ITU-R BS.775 (the song format holds 1-2 channels), with a warning and `provenance.source.downmix`. A damaged tail keeps what decoded, with a warning.
- D-144 Cover: JPEG or PNG up to 2 MB kept byte for byte; any other picture (BMP, WebP, a 5 MB scan) re-encoded once to JPEG at most 1400 px through PyAV, because SONG_FORMAT allows only JPEG/PNG <= 2 MB. A cover is artwork, not audio.
- D-145 Fail early, keep late: given lyrics are parsed during `decode` (explicit text/lrc that holds nothing singable fails with `lyrics_missing` before separation) and missing models are checked before separation (`models_missing`); but an alignment failure after minutes of separation saves the song without lyrics plus a warning (the sync editor's realign can add them), and so does a transcription that hears no words.
- D-146 `stems_sum_to_source` is true for all three presets: each defines `other` as the residual, and the writer computes it from the source minus what the other stems decode to. The pipeline decodes the written file again and refuses it (`write_failed`) if the sum misses the source by more than 2^-22; measured max error 5.96e-08 (half a 24-bit step) on the 4-minute song and every test song.
- D-147 Output: names follow the app's export rules (export.rs) plus no leading dots (the library skips dotfiles); the song is written under a short temporary name `studio-<random>.jksong.tmp-<pid>` (a 150-character title in a deep Library folder would break Windows' 260-character path limit) and moved with MoveFileExW(WRITE_THROUGH) without REPLACE_EXISTING, trying ` (2)`, ` (3)`..., so another song is never overwritten even if one appears meanwhile.
- D-148 VRAM is given back after separation, transcription and alignment (models deleted, gc, `torch.cuda.empty_cache`). Separation models are loaded per job (1.9 s from the SSD cache, measured) rather than kept between songs.
- D-149 `permissive` preset: Kim's Mel-RoFormer (MIT; 13.29 dB vocal SDR, above the Apache-2.0 Duality's 13.18 dB, faster, less VRAM) + SYH99999 drums (Apache-2.0); no permissive lead/backing splitter exists, so all vocals go to `lead_vocal` and `backing_vocals` is silent, said in the preset description the app shows (`hello.ok` presets) and MODELS.md. `PERMISSIVE_PRESETS` renamed `COMMERCIAL_USE_PRESETS` (it held GPL weights). Open, for the song-format owner: `jukeoke-cli verify` warns "unknown preset 'permissive'" (crates/jk-format/src/verify.rs accepts only full/clean, SONG_FORMAT 4.1 lists only those), so a permissive song fails `--strict` on that one warning; the APP_API `studio_submit` preset list and the UI need the value too.
- D-150 48 kHz and other non-44.1 kHz sources: the mix is converted once to the model rate; every model runs there (the karaoke model on the vocal estimate, the drum model on mix minus vocals computed at the model rate); vocals, lead and drums come back once each. Measured on a 48 kHz excerpt: provenance.resampling = 48000->44100 once, 44100->48000 three times (was a 44.1->48->44.1->48 chain for lead/backing). 44.1 kHz sources are unchanged bit for bit.
- D-151 No silent downloads: `ensure_model` downloads only with `allow_download=True`, which only `models.download` (and the developer's `models fetch`) pass; a missing file is `models_missing`, a damaged one `model_checksum` (not replaced behind the user's back). HT-Demucs `.th` pickles are hashed from the exact bytes that are then unpickled (weights_only cannot load them: they store the model class and numpy scalars).
- D-152 Alignment / Whisper weights: own registry (`modelzoo/hfmodels.py`) pinning commit, size and SHA-256 of every file, Hugging Face cache layout under `<Models>/hf`, loaded from the snapshot folder (no name resolution; `HF_HUB_OFFLINE=1`), downloaded with the same `.part` + SHA-256 + rename. On the build PC `$JK_BUILD/models-cache/hf` is a directory junction to the alignment benchmark's cache (no re-download of 6 GB).
- D-153 Portable caches: `--root` (and the supervisor's environment) point HF_HOME, TORCH_HOME, XDG_CACHE_HOME, CUDA_CACHE_PATH, NUMBA_CACHE_DIR, MPLCONFIGDIR, PYTORCH_KERNEL_CACHE_PATH, TRITON_CACHE_DIR, TORCHINDUCTOR_CACHE_DIR to `<root>/Settings/cache/*`, TMP/TEMP/TMPDIR to `<root>/Settings/tmp/studio`, HF_HUB_CACHE/TRANSFORMERS_CACHE to `<root>/Models/hf`; `sys.dont_write_bytecode` in code (python -I ignores PYTHON* variables). In dev mode the supervisor uses `$JK_BUILD/models-cache` as the models folder.
- D-154 realign anchors: when all anchors cannot hold, they are kept greedily in line order (kept if the letters before it fit after the previous kept anchor and the letters from it on fit in the rest of the song; CTC needs one frame per letter plus one between equal neighbours), so on a conflict the earlier anchor wins; dropped lines are returned (`dropped_anchors`) with a warning. The result is `checked: true`; its source defaults to the song's existing source.
- D-155 Lyrics: in `auto`, given LRC or text that normalises to no lines falls through to the next source; and an LRC with timestamps whose lines are all empty or headers no longer falls back to reading the raw text (which turned "[00:05.00][Chorus]" into a sung line). `lyrics.source` (e.g. `online:lrclib`, `embedded`) is a new optional field of `job.submit`.
- D-156 `shutdown` cancels the running job, waits up to 4 s for its clean-up, answers, exits 0; waiting jobs are dropped silently because the app owns the queue and re-sends them to the next process.
- D-157 Test stand-ins: `JUKEOKE_STUDIO_STUB=1` swaps in linear stand-in stems, the real aligner on a flat log-probability matrix and a "la la la" transcriber, so the whole server and pipeline (decode, lyrics, constraints, analysis, writer, naming, queue, cancel) run on the CPU in seconds; `JUKEOKE_STUDIO_FAKE_HW` fakes the probe. Song provenance names the stand-ins.
- D-158 Speed, measured 2026-11-17 with `make` in portable mode on Cortez "Feel (Stripped)" (JamendoLyrics, CC BY, 4:00.6, MP3), preset full, RTX 5070 Ti: plain-text lyrics 193.3 s in total (decode 0.3, separate 171.2 incl. 2.1 s model load, align 7.8, analyse 2.5, write 11.5); no lyrics (Whisper transcription) 228.7 s (decode 0.3, separate 175.0, transcribe 17.2, align 17.3, analyse 6.3, write 12.6). Song file 109 MB; stems sum error 5.96e-08; word onsets vs the annotation (text run, 355 words): median 0.045 s, max 0.200 s. Separation is ~15 s slower than the separation benchmark's 152-160 s; other workstreams' processes were running on this PC at the time, so the gap is not attributed. First run on a fresh stick also writes ~183 MB of CUDA JIT cache to `Settings/cache/cuda` (driver default limit 256 MB): budget for it on the stick.

- D-178 The cache holds the shifted pitched mix, not per-stem shifts: per-stem shifting differs from the real-time waveform by +0.5 to +1.5 dB residual relative to the signal on a real song (`keycache_linearity` example) and costs 3x the CPU. - D-180 Cache files are append-only 32768-frame cells with a cell map in `index.json`: preallocating and writing mid-file made NTFS/exFAT zero-fill up to the write offset synchronously (seconds on a slow stick). Covered cells are never rewritten, so a reader never sees a torn cell.
- D-181 A render run starts at a cell exactly like a real-time seek (reset, prime from start - prime_len); an interrupted run keeps its last cell in memory as a tail; where runs meet, the earlier run crossfades its last 40 ms into the later run's pre-roll (click-free, but not identical to an uninterrupted real-time play there).
- D-182 Switch rule: 5 s rendered ahead with a renderer above 1.1x real time, otherwise contiguous coverage to the end of the song. While paused the switch is an in-place segment restart on the cached key (as D-63); while playing, a feed starting at the next worker block at least 0.1 s ahead.
- D-183 Seeks start on the cached key (new key, else the one heard before) when it is ready at the target; otherwise on the previous key, with the renderer moved to the target first. A cache miss fades to the bypass (key 0) so the fade ends where the data ends (never observed in the tests).
